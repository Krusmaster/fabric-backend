# Getting started: what Krusgraph reads and what your admin turns on

Read this before the first build. It says what Krusgraph reads and with which permission, which Fabric tenant settings each output needs, the limits, and how to start with a small set of tables.

## Before you start

A Microsoft work account, a workspace on a Fabric capacity (an F SKU, a P SKU or a trial capacity; Learn: per-user licences such as Power BI Pro and PPU don't provide Fabric capacity), and an administrator who approves the Krusgraph app in Microsoft Entra ID once (admin consent). The connection itself is on [the set-up guide](/start).

## What Krusgraph reads, and with which permission

Planning reads names and types: the workspace's items, each source's schemas, tables and columns. Checking runs read-only counting queries (`COUNT`, `GROUP BY`) on the tables you check. Every call runs as the signed-in person with delegated permissions, so Krusgraph reaches nothing that person cannot already reach. Nothing is created until a creating tool is called with `dry_run=false`.

The permissions, what each is used for and why, are listed for your IT department on [/it](/it#permissions).

## Every schema is listed

When `plan_backend` is called without a schema and the source has more than one, it lists every schema with its tables and plans nothing until you choose one.

## Limits

`validate_plan` counts up to 60 keys and links per call by default (200 at most), keys first, and lists what it did not count; call it again with `resume_from` for the rest.

Rule R5 in `plan_backend` reads the first 200 distinct values of a candidate column with at most 20 counting queries.

`plan_backend` answers in full up to 60 tables and as a summary above that (`detail`).

## What is not supported

Reading or changing tenant settings, capacity settings or Entra settings. Application permissions (every call is a person's). Writing to a source table: the creating tools add new items and never write over the tables they read.

## How to scope to 20 tables

Name the tables, or a glob such as `sales_*`, in `tables`: `plan_backend` then shows only those, and `validate_plan` counts only their keys and links. Planning still reads the names and types of the whole schema, so a link to a table outside the 20 is not lost.

Example: "Plan the 20 tables `sales_*` and `customer` in the schema `dbo`, then check them."
