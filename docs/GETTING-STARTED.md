# Getting started: what Krusgraph reads and what your admin turns on

Read this before the first pilot. It says who does what, in order, to try Krusgraph on your own Fabric data; what Krusgraph reads and with which permission, which Fabric tenant settings each output needs, the limits, and how to start with a small set of tables.

## Before you start

A Microsoft work account, a workspace on a Fabric capacity (an F SKU, a P SKU or a trial capacity; Learn: per-user licences such as Power BI Pro and PPU don't provide Fabric capacity), and an administrator who approves the Krusgraph app in Microsoft Entra ID once (admin consent). The connection itself is on [the set-up guide](/start).

## Two ways to run it

**The hosted MCP server, available now.** Your AI client (Claude, or another MCP client) connects to Krusgraph and you work in chat; [the set-up guide](/start) has the address and the steps. Everything on this page works on this path.

**The Krusgraph Model item inside Fabric.** The same engine as an item type in your workspace (+ New item → Krusgraph Model). Its listing in Fabric's Workload Hub is pending, so it cannot yet be added from the Hub. What your administrator does for it, and how to try it before then, is on [the Fabric pilot page](/pilot/fabric).

## Steps for a first pilot, in order

Who does what, from "we have Fabric" to the first items built. Each step says which error a missing step answers with: every error has a `kind`, a stable name, and a `hint` that says what fixes it.

1. **Approve the app once (admin consent)** (Entra administrator). A Global Administrator or Privileged Role Administrator grants admin consent for the Krusgraph app in Microsoft Entra ID, once for the organisation. The permissions it asks for, all delegated: Microsoft Graph: `User.Read`; Fabric: `Workspace.Read.All`, `Item.Read.All`, `GraphQLApi.ReadWrite.All`, `GraphQLApi.Execute.All`, `Notebook.ReadWrite.All`, `DataPipeline.ReadWrite.All`, `Item.ReadWrite.All`; Azure SQL Database: `user_impersonation`. Why each is needed, and how to revoke it: [For your IT department](/it#permissions). Errors that point here: `consent`.
2. **A capacity, a workspace and a role** (Fabric administrator). A workspace on a Fabric capacity (F SKU, P SKU or trial), with a lakehouse or warehouse that has test or sample tables. Viewer on the workspace is enough for the data lead to plan; creating items needs Contributor. Errors that point here: `capacity`, `no_access`.
3. **Turn on the tenant settings for the outputs you want** (Fabric administrator). Admin portal → Tenant settings, from the table under "Tenant settings per output" below. For a first API for GraphQL, semantic model and report that is **Users can create Fabric items**. Krusgraph cannot read these settings: when one is off, Create is refused (HTTP 403) and the answer quotes Fabric's own error code. Errors that point here: `feature_disabled`, `fabric_refused`.
4. **Connect, and try the synthetic sample first** (Data lead). Add Krusgraph to your AI client as [the set-up guide](/start) says and sign in with your work account. Then ask "Show me on the synthetic shop sample" (the `start` tool with `sample=true`): the whole path on synthetic data, reading nothing in your Fabric. In the Fabric item, "Is everything ready? Check this workspace" reads consent, capacity, workspace and lakehouse instead, and changes nothing. Errors that point here: `sign_in`.
5. **Choose your data and check it against the rows** (Data lead). Say "start Krusgraph". The `start` tool lists your workspaces, sources and schemas to choose from (start with about 20 tables; see "How to scope to 20 tables" below). `plan_backend` proposes keys and relationships, each with the rule that found it; `validate_plan` counts them against the rows: unique keys, empty keys, references that find no row. You decide on each one. Errors that point here: `not_found`, `schema_not_found`.
6. **Dry run, create, then verify** (Data lead). The dry run shows every item that would be created, and the tenant settings it needs. Nothing is created until you confirm the names (`dry_run=false`). Afterwards `verify_build` reads back what was built and compares it with the dry run, by rules, not by AI. Errors that point here: `consent`, `feature_disabled`.

## What Krusgraph never does

**Shows no row values unless you ask.** The guided path and the check return counts, not row values. Rows come back only from a tool you ask for them: `sample_rows` (up to 20 rows of one table, with columns that look like personal data masked by name) or `query_graphql` (the query you ask for).

**Deletes nothing.** No MCP tool deletes an item in Fabric, and the creating tools never write over the tables they read. In the Fabric item, only the data product page's Delete from Fabric deletes, after a dry run and the data product's name typed.

**Uses only your permissions.** Every call runs as the signed-in person, with delegated permissions; the app has no application permissions, so it reaches nothing that person cannot already reach.

**Creates nothing on its own.** Every creating tool answers with a dry run first; only `dry_run=false` creates, and the guided path asks you to confirm the names before that.

**Leaves your settings alone.** It never reads or changes tenant settings, capacity settings or Entra settings.

## What Krusgraph reads, and with which permission

Planning reads names and types: the workspace's items, each source's schemas, tables and columns. Checking runs read-only counting queries (`COUNT`, `GROUP BY`) on the tables you check. Every call runs as the signed-in person with delegated permissions, so Krusgraph reaches nothing that person cannot already reach. Nothing is created until a creating tool is called with `dry_run=false`.

The permissions, what each is used for and why, are listed for your IT department on [/it](/it#permissions).

## Every schema is listed

When `plan_backend` is called without a schema and the source has more than one, it lists every schema with its tables and plans nothing until you choose one.

## Limits

`validate_plan` counts up to 60 keys and links per call by default (200 at most), keys first, and lists what it did not count; call it again with `resume_from` for the rest.

Rule R5 in `plan_backend` reads the first 200 distinct values of a candidate column with at most 20 counting queries.

`plan_backend` answers in full up to 60 tables and as a summary above that (`detail`).

## What is not supported

Reading or changing tenant settings, capacity settings or Entra settings. Application permissions (every call is a person's). Writing to a source table: the creating tools add new items and never write over the tables they read.

## How to scope to 20 tables

Name the tables, or a glob such as `sales_*`, in `tables`: `plan_backend` then shows only those, and `validate_plan` counts only their keys and links. Planning still reads the names and types of the whole schema, so a link to a table outside the 20 is not lost.

Example: "Plan the 20 tables `sales_*` and `customer` in the schema `dbo`, then check them."

## In the dry run

The guided path's dry run names, in one line, the tenant settings its outputs need, and says that their value was not checked. For a chosen set of outputs, `fabric_backend.tenant_settings.markdown(outputs)` writes the request to your administrator in order.
