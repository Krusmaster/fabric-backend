Get started

Small steps. Useful connections.

A clearer start with {{PRODUCT}}: three steps, and it runs inside Claude with your own Fabric permissions.

Start with your Microsoft account

{{PRODUCT}} uses your signed-in Microsoft work account to reach the Fabric workspaces you can already see. Nothing is created in our name: every call runs as you.

Your Microsoft Entra admin grants consent once for your organisation: Grant admin consent in Entra

That link opens Microsoft's own consent page for the {{PRODUCT}} app; there is no sign-in on this site. It allows {{PRODUCT}} to call Microsoft Fabric and SQL as each signed-in user, nothing more, and the admin can revoke it at any time under Enterprise applications in Entra. Already consented? Then there is nothing to do in this step.

Choose a workspace

You need access to the Fabric workspace you want to use (Viewer is enough to plan, Contributor to create), and that workspace needs a Fabric capacity (a trial is fine). Have the workspace name or id ready; a lakehouse, warehouse or SQL database in it is the source.

No workspace yet? The demo on /explore runs on a synthetic schema and needs no account, and fabric-backend demo runs the same engine on your own laptop against a SQL Server or a folder of files (/local).

Open in Claude

In Claude, open Settings → Connectors → Add custom connector, give it a name and paste this URL:

{{MCP_URL}}

Claude asks you to sign in with your Microsoft work account. After that you can say “List the data sources in workspace …”, “Plan a backend over the shop lakehouse” (nothing is deployed) or “Create it as shop_api”. Five first questions that pay off on a lakehouse nobody has documented are in the docs.

Claude is the client this is built and documented for. Claude Code and Cursor use the same URL but sign in through a local redirect that is not registered on the Entra app yet; until it is, use Claude. Full usage notes are in the docs.

What will {{PRODUCT}} access?

Only what the signed-in user can already reach. The Entra app asks for these delegated permissions, all granted by your admin once and all acting as the user:

PermissionUsed for
User.Read (Microsoft Graph)sign-in only
Workspace.Read.All, Item.Read.All (Fabric)listing sources and reading item metadata
GraphQLApi.ReadWrite.All (Fabric)creating or updating the one API for GraphQL item you ask for; never deleting
GraphQLApi.Execute.All (Fabric)running the read-only queries you ask for
user_impersonation (Azure SQL Database)reading table and column names from the SQL analytics endpoint

Why each one: Workspace.Read.All and Item.Read.All are what list_workspaces, list_sources, describe_backend, plan_drift and lineage read; GraphQLApi.ReadWrite.All is used by create_backend alone; GraphQLApi.Execute.All by query_graphql and app_readiness; the SQL permission by every tool that reads table and column names or counts rows (list_tables, plan_backend, validate_plan, sample_rows, the drafts). The creating tools for semantic models, ontologies and data agents need Item.ReadWrite.All, which the app does not ask for today: they answer with a dry run, and with consent naming that scope if asked to create.

What passes through the server: workspace, item, table and column names, and the results of queries you run. Your tokens are exchanged on your behalf and held in memory only. There is no database of our own and nothing is written to disk. Details in the privacy policy.

Two steps stay manual in the Fabric portal because there is no API for them yet, and the connector tells you when they are needed: turning on introspection for the GraphQL item, and granting permissions on it to other apps.
